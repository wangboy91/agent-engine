# Agent Engine 技术设计与生产化

> **文档状态**：仍有效。1.0.1 实施任务与 API 前缀见 [技术实现文档_1.0.1](技术实现文档_1.0.1.md)。

## 1. 技术栈与运行形态

| 类别 | 当前选择 |
| --- | --- |
| 语言与依赖管理 | Python >= 3.12、uv |
| 数据模型与校验 | Pydantic v2、jsonschema |
| CLI / API | Typer、FastAPI、Uvicorn |
| HTTP 客户端 | httpx |
| 模型协议 | Mock、OpenAI-compatible、Anthropic-compatible |
| 当前持久化 | JSON 文件、本地文件系统、内存测试实现 |
| 测试 / 质量 | pytest、ruff、mypy strict |

虽然依赖中已声明 SQLAlchemy 与 Alembic，但当前代码尚未使用它们实现持久化。它们应视为数据库迁移的预留依赖，不能据此认为服务已经具备数据库能力。

## 2. 包契约

### 2.1 Skill

Skill Loader 读取 `SKILL.md` 的 YAML frontmatter 与 `agent.skill.json`。前者只包含面向生态互操作的 `name`、`description`；后者包含 Agent Engine 专属运行配置。Loader 会解析相对 Schema 路径、校验 ID、版本、工具白名单、执行配置和 Workflow 定义。

Skill 的最终输出必须是 JSON object 且通过 output schema。模型原始文本若不是合法 JSON，会被运行时视为失败；这有意牺牲“尽量返回一些文本”的宽容性，换取下游自动化的确定性。

### 2.2 Tool

Tool 使用 `tool.yaml` 描述 id、type、entry、runtime、permissions 和 schema。Python runner 做以下保证：输入 schema 校验、子进程调用、超时 kill、stdout JSON 解析、输出 schema 校验。API runner 使用 httpx，支持 JSON 请求和环境变量 API key header。

生产建议：

- 给每个 Tool 添加版本、维护者、风险级别、网络出口白名单与最大资源配额；
- 把外部服务的认证统一改为 Secret reference，禁止 YAML 和环境散落长期密钥；
- 对写操作要求幂等键，并把外部请求 ID 写入 trace；
- 对 API Tool 增加路径参数、header/query 映射、响应转换、重试/熔断和 SSRF 防护。

### 2.3 OpenAPI 导入边界

`import_openapi_tools()` 可从简单 OpenAPI paths 生成 Tool，提取 application/json request/2xx response schema。它不等同完整 OpenAPI 执行器：不处理 `$ref` 解析、服务器选择、path 参数填充、多媒体、OAuth、分页或复杂响应。因此导入后必须人工审查生成 Tool 的 URL、认证和 schema。

## 3. 模型网关

`ModelRouter` 根据 profile 选择 provider，将内部的 messages、tool definitions 和 `ModelResponse` 归一化。Provider 对连接、超时、HTTP 错误映射为 `AgentEngineError` 并标记可重试性。

真实模型接入验收应覆盖：

1. 与供应商实际 tool-calling 字段兼容；
2. 非流式与流式 response 的用量、finish reason、tool call 多轮行为；
3. 超时、429、5xx、结构化错误和网络失败；
4. 最大 token / 成本限制是否可信；
5. 模型拒绝输出或输出不符合 schema 时的修复/降级策略。

当前单元测试覆盖 provider 请求映射，但没有使用真实供应商凭据做集成验收。每个上线 profile 应有隔离环境的 contract test，且不得在 CI 日志写出密钥或完整 prompt。

## 4. 工作流与可靠性

运行时支持直接模型循环、direct tool 与 Workflow/DAG。它能保存最终 Run、错误和 trace，也支持 Tool policy 导致的审批暂停。

需要正视的可靠性边界：

| 能力 | 当前情况 | 生产要求 |
| --- | --- | --- |
| 内存中断恢复 | 仅保留最终/等待审批状态 | 逐步骤 checkpoint、队列 job、可恢复状态机 |
| 副作用幂等 | 由 Tool 自行保证 | 引擎传递 idempotency key，持久化外部调用记录 |
| 重试 | 对可重试模型错误有基础逻辑 | 分类重试、指数退避、预算、死信队列 |
| 取消 | 未形成跨 API/worker 的取消协议 | cancel token、Tool 中断、补偿策略 |
| 长任务 | API 进程内执行 | queue + worker + polling/SSE 状态通道 |
| 并发控制 | DAG 局部并发 | workspace、模型、Tool、租户维度配额 |

Workflow 设计必须明确每一步的输入契约、输出命名空间和失败策略。不要把“依赖上一步所有平铺字段”当作长期 API；应逐步引入引用表达式或显式 mapping，以避免字段覆盖。

## 5. 安全设计现状与上线要求

### 当前已有控制

- Tool 白名单由 Skill `tools.allow` 限制；
- workspace/identity 可限制可见 Skill；
- Policy 支持 allow/ask/deny，Secret reference 只允许 Tool 显式声明的 secret；
- Python Tool 有 timeout，Trace 对常见敏感键脱敏；
- `.agent/`、`.env` 和 `data/` 不应提交到版本库。

### 关键缺口

1. HTTP 路由没有认证、用户身份验证或授权中间件；
2. 本地 SecretStore 明文保存，系统级环境变量仍可能注入子进程；
3. Python Tool 仅是子进程隔离，可执行宿主机权限范围内的任意代码；
4. API Tool 未做 URL/网络出口治理，导入不可信规范可能造成 SSRF；
5. JSON 文件没有并发锁、加密、审计不可篡改性与备份；
6. 没有速率限制、请求大小限制、CORS 安全策略或租户配额。

### 上线安全基线

- API Gateway 做 OIDC/JWT、TLS、CORS、WAF、rate limit；应用层从可信 token 构造 `RunContext`，禁止客户端任意传 workspace/identity；
- RBAC/ABAC 至少覆盖 workspace、identity、Skill 版本、Tool policy、审批和 artifact 下载；
- 接入 KMS/Vault，Secret 只在执行瞬间注入且不写 trace；
- Python Tool 使用无特权容器/microVM，禁用宿主挂载，限定 CPU/内存/时间/网络和可写 artifact 目录；
- API Tool 使用允许域名、DNS/IP 校验、出网代理、请求大小与响应大小限制；
- 记录不可变审计事件：谁在何时用什么授权执行何版本 Skill、调用何 Tool、审批了什么。

## 6. 数据与可观测性

当前 Run、Trace、Artifact 是调试的最小闭环。生产化应建立以下数据模型：

- `skill_packages` / `tool_packages`：包 ID、版本、校验和、来源、发布状态；
- `workspace_resources` / `identity_grants`：安装、启停、授权；
- `runs` / `run_steps` / `tool_calls`：状态机、父子关系、重试、幂等键、成本；
- `artifacts`：对象存储 URI、媒体类型、大小、保留期、访问控制；
- `policy_rules` / `approvals` / `audit_events`：决策依据和操作者；
- `secrets`：仅元数据与引用，不存 value。

建议把 OpenTelemetry trace/span 与 Run ID 对齐，并至少监控：请求量、运行成功率、P50/P95 时延、模型/Tool 错误、排队时间、token/cost、审批等待时间、artifact 存储量和安全拒绝次数。

## 7. 部署建议

### 受控试运行

单机 Docker/VM，API 一个副本，可信管理员使用。把 `.agent` 和 `data/artifacts` 放到持久卷，反向代理提供 TLS 与基础认证。仅开放经验证的 Skill/Tool，不允许用户上传 Python Tool。

### 生产部署

拆分 API、worker、数据库、对象存储和 secret manager。API 只负责鉴权、提交、查询与流式状态；worker 执行模型与 Tool；所有长任务由队列调度。部署应支持滚动升级、schema migration、数据库备份恢复、对象存储生命周期和灰度发布。

### CI/CD 门禁

每次合并至少运行：

```bash
uv --cache-dir .uv-cache run --extra dev pytest
uv --cache-dir .uv-cache run --extra dev ruff check .
uv --cache-dir .uv-cache run --extra dev mypy app
```

发布包前额外运行：包 loader 契约测试、真实 provider 的隔离 contract test、镜像漏洞扫描、Tool 静态审查和端到端 smoke test。生产变更必须可回滚：数据库 migration、Skill/Tool package 和模型 profile 都需要版本化。
