## 1. 评估范围和证据

评估基于当前工作区源代码、资源包、测试与默认配置，不包含外部模型供应商的真实线上连通性。2026-07-28 在项目根目录执行：

## 2. 现状结论

### 可以立即使用的范围

- 本地开发/演示：加载本地 Skill/Tool，使用 Mock 或已验证的兼容模型执行；
- 单机受控服务：为固定业务线提供 HTTP API、SSE/WS 运行状态、审批与本地 artifacts；
- 内容生产工作流原型：`content-video-workflow` 展示了 DAG 编排与结构化中间产物；
- SDK/CLI 自动化：适合 CI smoke test、内部脚本和开发调试。

### 不能直接承诺的范围

- 公网、多租户 SaaS；
- 不可信用户上传/执行 Python Tool；
- 多副本、高并发或长时间异步任务；
- 存储敏感业务 secret 的正式环境；
- 对真实模型供应商的稳定性、成本和结构化输出质量 SLA；
- 通用自主 Agent 或复杂企业级 OpenAPI 自动调用。

## 3. 成熟度矩阵

| 模块 | 评级 | 证据 | 主要缺口 |
| --- | --- | --- | --- |
| 包规范、Schema、注册 | A- | loaders、registries、127 项测试 | package 签名、版本发布与依赖锁定 |
| Skill Runtime | B+ | tool loop、DAG、审批恢复、重试测试 | durable checkpoint、取消、幂等 |
| Tool Runtime | B | Python/API runner、timeout、schema | sandbox、SSRF/网络治理、熔断 |
| 模型网关 | B | 三协议与 provider 测试 | 真实环境 contract test、fallback、成本控制 |
| Agent | B- | 场景、关键词、输入解析、session | LLM routing 评测、多步规划、记忆检索质量 |
| Workspace/Policy | B- | identity bind、allow/ask/deny、审批 | 真正认证授权、完整审计、租户隔离 |
| HTTP/流式控制台 | B | REST、SSE、WebSocket、静态 UI | auth、限流、版本化、运营监控 |
| 数据持久化 | C | JSON/local 实现可用 | DB、事务、并发、备份、迁移 |
| 生产运维安全 | D | 基础脱敏与 policy | KMS、沙箱、告警、灾备、合规 |

评级含义：A=可作为稳定内核；B=受控环境可用；C=原型适配器；D=生产前必须建设。它用于排优先级，不是质量评价。

## 4. 建议的上线阶段

### Phase 0：固定业务线试运行（1–2 周）

目标：单 workspace、受控内部用户、固定 Skill/Tool 集合，拿到真实运行数据。

验收：

- 用真实模型 profile 跑通 3–5 个代表性输入，结果通过 Schema 和人工质量抽检；
- Tool 仅允许代码审查过的包，所有外部写操作具备幂等键；
- 反向代理启用 TLS 和管理员认证，不对公网裸露 FastAPI；
- 输出统一记录 Run ID，能够从 Run 查询 trace 与 artifacts；
- 建立日成本、失败率、审批等待时间的人工巡检。

### Phase 1：可控上线（2–4 周）

目标：将“能跑”变成“可安全恢复地跑”。

必须完成：

1. PostgreSQL Store（Run、Trace 索引、workspace、policy、session）和 migration；
2. 对象存储 Artifact；
3. OIDC/JWT + workspace/identity 授权；
4. KMS/Vault SecretStore；
5. 队列与 worker，长任务脱离 API 进程；
6. 结构化日志、metrics、告警和审计事件；
7. Tool 网络白名单与容器化执行策略。

### Phase 2：业务复制（4–8 周）

目标：多个业务线能安全地安装、评测和发布不同资源包。

必须完成：

- Skill/Tool package registry、版本、签名/审核、灰度与回滚；
- 多维配额：租户、用户、模型、Tool、并发与成本；
- 评测集、回归测试和模型 profile 发布流程；
- 场景配置中心和确定性路由治理；
- 运行质量看板、失败重放和人工接管。

### Phase 3：平台化（持续）

目标：以评测驱动增强 Agent、记忆和多模态能力，同时不降低确定性和可观测性。

方向包括：检索/记忆服务、LLM router、计划与多动作执行、Tool marketplace、审批工作流、成本优化和跨 workspace 策略继承。

## 5. 近期迭代 Backlog（建议排序）

| 优先级 | 事项 | 产出 | 验收标准 |
| --- | --- | --- | --- |
| P0 | 认证与授权 | FastAPI auth middleware、context builder、RBAC | 未授权无法读取/运行其他 workspace 资源 |
| P0 | Secret 改造 | Vault/KMS adapter，迁移脚本 | secret value 不落 DB/trace/log，能轮换 |
| P0 | Tool 隔离 | 受限容器 runner、网络策略 | 不可信 Tool 无法访问宿主/任意网络 |
| P0 | DB + migration | SQLAlchemy repository adapters | 多副本下 Run/审批状态一致、可备份恢复 |
| P1 | 异步执行 | job schema、queue、worker、取消 | API 重启不丢长任务，可重试可查询 |
| P1 | Artifact 对象存储 | S3/OSS adapter、签名下载 | 访问经鉴权、可设置保留期 |
| P1 | 观测 | OTel、Prometheus、告警规则 | 可按 run/workspace/tool/model 查询失败和成本 |
| P1 | 包生命周期 | 发布、版本、审核、回滚 | 同一 run 可追溯精确包版本 |
| P2 | 路由评测 | benchmark、路由日志、fallback | 路由变更不会降低关键场景成功率 |
| P2 | OpenAPI 增强 | 引用解析、参数映射、SSRF 防护 | 复杂 API 可安全生成/执行 Tool |

## 6. 迭代工作方式

每项改动按以下最小闭环交付：

1. 在 issue/变更说明中明确用户价值、接口变化和数据迁移；
2. 先更新 domain schema/Port，再实现适配器与接口；
3. 为成功、失败、权限拒绝、重试/恢复分别写测试；
4. 更新 README 与本目录的技术文档；
5. 使用 feature flag 或版本化资源包灰度；
6. 发布后以 Run/Trace 指标验证，再决定扩大范围。

不要为了接入新业务在 HTTP handler 或 UI 中硬编码 Skill 逻辑。业务差异应进入资源包、scene mapping 或明确的 application use case；这会保持引擎在持续迭代中仍是可维护的基座。
